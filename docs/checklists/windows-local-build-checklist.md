# Windows Local Build And Database Rebuild Plan

Status: planned. No build, database rebuild, restore, or application smoke test has been performed under this plan.

## Goal And Boundaries

Make the repository-based Electron app work on Windows with the same application workflows as the working Mac local build. This is a local build, not an installer. The Mac PostgreSQL database remains authoritative; Windows uses its own local database and does not synchronize database changes back to the Mac. See [ADR 0001](../adr/0001-local-mac-database-no-cross-device-sync.md).

The existing Windows `movies` database is disposable for this task. Its schema fails the current checks, so build and validate a **new named database** rather than running an in-place migration against it. Do not drop the old database or uninstall either PostgreSQL service as part of this plan; other applications may use those services. An empty database proves startup, but a current Mac backup is needed to verify recommendations and other data-backed workflows with current data.

## Safety Rules

- Do not run `git` commands without explicit permission in the current conversation.
- Move replaceable runtime artifacts into repository-root `.trash/`, preserving their relative paths where practical. Do not delete them. Do not move `.env`, `.secrets/`, `data/cache/`, database backups, imports, or other source-of-truth data into `.trash/` without explicit approval.
- Keep database credentials out of shell transcripts, reports, and this checklist. Use an authenticated client or process-local configuration.
- Perform database work only against a newly named Windows database after verifying the server, port, database name, and role. Keep the old `movies` database intact as a rollback reference.
- Do not start a restored database against the real Google Sheet until `sheet_sync_outbox` has been inspected. FastAPI starts a background outbox flush at startup; pending tasks can write to the Sheet. Use a test Sheet for write-path testing.

## Phase 2: Prove Startup With A Fresh Empty Database

- [ ] Create a distinct empty database, such as `movies_windows_schema_test`, on an authenticated local PostgreSQL instance. Do not reuse or clear `movies`.
- [ ] Point a process-local `MOVIES_POSTGRES_DSN` at that exact database and set `MOVIES_RECOMMENDATION_BACKEND=postgres`. Run `.\.venv\Scripts\python.exe -m jobs.init_database` twice. The second run checks repeatability; neither run is a complete schema drift audit.
- [ ] Compare the resulting database with `PostgresViewingHistoryRepository.initialize_schema()` and `initialize_interaction_schema()` in `backend/app/db/postgres_repository.py`. Check all ten active tables, key column types and nullability, primary/foreign/unique constraints, and indexes. In particular, require `sheet_sync_outbox`, nullable `viewing_history.deleted_at`, and a **non-unique** `idx_viewing_history_source_row`.
- [ ] Before launching the API, verify port 8000 is free or belongs to this app. The Electron shell can reuse an existing backend at that port.
- [ ] Start FastAPI with Selenium prewarm disabled for the first smoke test. Confirm `/openapi.json` and `/wishlist` return HTTP 200, then stop it cleanly. An empty candidate pool is expected to have no useful recommendations; that is not a full app acceptance result.

If the new database fails schema validation, capture the discrepancy and its cause first. Then recreate **only that newly named test database**, rerun initialization, and audit again. Investigate a repeat failure before proceeding; do not silently treat an HTTP 200 health response as proof of schema correctness.

- [ ] A newly built/restored Windows database passes the explicit schema audit; the original Windows `movies` database remains untouched.

If a phase fails, keep the existing Windows database and Mac source unchanged, retain the failing new database for inspection until the cause is known, and restore previous runtime artifacts from `.trash/` if needed. Report the failed command, affected target, and evidence before another attempt.
